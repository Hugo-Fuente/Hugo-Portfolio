Decisões de Engenharia.

Garantir que o dinheiro não é criado do nada, perdido ou gasto duas vezes exige mais do que um CRUD simples. A API foi desenhada para suportar alta concorrência e falhas de rede.

// CONCORRÊNCIA SEGURA

Travas Pessimistas (Locking)

Toda operação que altera saldo inicia com SELECT ... FOR UPDATE no banco, ordenado pelo ID da conta. Isso serializa as transações concorrentes na mesma linha, eliminando deadlocks e impedindo que dois Pix simultâneos gastem o mesmo saldo.

// RESILIÊNCIA DE REDE

Idempotência Estrita

Proteção contra "duplos cliques" e timeouts. As chaves de idempotência, combinadas com hash do corpo da requisição e constraints UNIQUE no banco de dados, garantem que reenvios legítimos não gerem cobranças duplicadas.

// INTEGRIDADE FINANCEIRA

Fato x Intenção

A entidade TRANSACAO é imutável (fato consumado). Pagamentos programados apenas movimentam o saldo de "Livre" para "Comprometido". O dinheiro nunca se sobrepõe e o saldo total é sempre reconstruível pelo extrato.

// GOVERNANÇA DINÂMICA

Motor de Aprovações

Em vez de "cargos fixos", o sistema lê dinamicamente as REGRA_APROVACAO baseadas em valor e meio de pagamento. Um Pix de R$ 5.000 pode interceptar automaticamente a transação e exigir votos de N sócios elegíveis antes da execução.

// DESIGN PATTERNS

Arquitetura em Camadas

Estrutura estrita e unidirecional baseada no base-service do bootcamp. O fluxo atravessa Middlewares de segurança, Schemas de validação JSON, é orquestrado no Resource, validado no Controller e finalmente persistido através do Repository e Models.

// DESIGN DE SOFTWARE

Monolito Modular

O dinheiro de uma conta precisa ser serializado em uma única transação de banco. Separar serviços (como saldo e agendamentos) exigiria transações distribuídas (Padrão Saga) desnecessárias para o escopo, priorizando consistência imediata.

A Experiência no Bootcamp.

Participar do Bootcamp QI Tech foi uma imersão completa na realidade de engenharia de uma instituição financeira. O desafio ia muito além de codar um CRUD: o objetivo era projetar e construir as engrenagens de um protótipo bancário trabalhando em equipe, tendo como fundação um Base Service arquitetado em camadas rígidas de produção (Middlewares, Resources, Controllers e Repositories).

Foi através desse processo prático de desenhar a Request for Comments (RFC), planejar entidades de banco de dados e bater cabeça com testes de concorrência simultânea — em conjunto com Leandro Apolinário Leite e Mateus Carósio — que essa API nasceu. Ter a presença e os conselhos de gigantes da área, como Gustavo Guanabara, trouxe uma carga extra de peso, responsabilidade e ambição à qualidade técnica do projeto.
